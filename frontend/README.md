# Frontend — Gestion de boutique

PWA React 18 + TypeScript strict + Vite + Tailwind CSS v4. Identité visuelle : `../design-system.md`
(les seuls tokens autorisés sont dans `src/shared/ui/tokens.css`). Node ≥ 24.

```bash
npm ci                     # installe les versions verrouillées (package-lock.json)
cp .env.example .env       # VITE_API_BASE=/api
npm run dev                # http://localhost:5173 — vitrine des composants : /_ui
```

| Commande                            | Rôle                                                                                                                                                                              |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run dev` / `build` / `preview` | développement, build de production (`dist/`), aperçu du build                                                                                                                     |
| `npm run lint`                      | ESLint + règles du design system (pas de classe arbitraire `[…]`, pas de `style=`, pas de `text-xs/sm`, pas de `<button>/<input>/<select>/<textarea>` bruts dans `src/features/`) |
| `npm run typecheck`                 | `tsc -b` (strict, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`)                                                                                                       |
| `npm run format` / `format:check`   | Prettier                                                                                                                                                                          |
| `npm test` / `test:coverage`        | vitest (jsdom) ; couverture ≥ 90 % exigée sur `src/shared/`                                                                                                                       |
| `npm run size`                      | size-limit après `build` : `dist/` ≤ 3 Mo, JS initial ≤ 250 Ko gzip                                                                                                               |
| `npm run check:length`              | échoue si un `.ts/.tsx` de `src/` dépasse 200 lignes                                                                                                                              |
| `npm run check:no-showcase`         | après `build` : prouve que `/_ui` est absent de `dist/`                                                                                                                           |
| `npm run icons`                     | régénère les icônes PWA **provisoires** depuis les tokens                                                                                                                         |
| `npm run gen:api` / `check:api`     | génère `src/core/api/schema.gen.ts` depuis `../backend/openapi.json` (exporté par `python -m tools.export_openapi` dans `backend/`) ; `check:api` échoue si le fichier est périmé |

Arborescence :

- `src/app/` : routeur, gardes (`guards.tsx`), coquille de boutique `/s/{shopId}/…`, pages provisoires, vitrine `dev/` ;
- `src/core/api/` : client `fetch` typé par le contrat **généré** (`schema.gen.ts`, jamais édité), `X-Device-Id` (UUIDv7 dans `localStorage`), `ApiError` / `NetworkError` ;
- `src/core/auth/` : session (jeton d'accès en mémoire, refresh **single-flight** puis rejeu, restauration silencieuse) ;
- `src/core/profile/` : `ShopProfile` (menus par rôle) — implémentation **provisoire** « motos » en dur jusqu'à `GET /shops/{id}/profile` ;
- `src/core/offline/` : connectivité (« Connexion nécessaire », aucune file d'envoi : `offline_capture` désactivé) ;
- `src/core/pwa/` : politique de cache (specs § 7.3), nouvelle version, « Recharger la dernière version », numéro de version ;
- `src/core/gateways/` : passerelles des écrans (specs § 4.6). Ventes : `httpSales.ts` (`POST/GET /sales`, fiche, `cancel`, `error-reports`, `receipt`, `GET /customers?q=`, `GET /members` ; `X-Captured-At` = heure de l'appareil avec son fuseau, via l'option `headers` du client) et `httpCatalog.ts` (points de vente = colonnes `is_point_of_sale` de `GET /stock` — le vendeur ne lit pas `/locations` —, lieu habituel = `default_location_id` de `GET /profile`, modes actifs de `GET /payment-modes`, recherche = `GET /articles?sort=best_selling&status=active` jointe au stock du lieu par `GET /stock?location_id=`). Demandes de prix (T16b) : `POST/GET /price-requests`, `GET /price-requests/{id}`, `POST …/decision {decision, version}` ; retours : `POST/GET /sales/{id}/returns`. Types : alias de `schema.gen.ts` (`salesContract.ts`, `returnsContract.ts`) ; `saleErrors.ts` lit les `details` d'erreur en fail-fast (dont `PRICE_BELOW_MINIMUM.price_request`, `RETURN_QUANTITY_EXCEEDED`, `OVERPAYMENT` d'un retour). `simulated/` (demandes de prix dans `simulatedPriceRequests.ts` ; retours absents de la vitrine) ne sert plus qu'à la vitrine `/_ui` et au faux serveur des tests (`src/testing/salesServer.ts`) : rien ne l'importe depuis l'application ;
- `src/features/sales/` : « Nouvelle vente » (`/s/{shopId}/nouvelle-vente`) — vendeur : son lieu habituel (sans lieu : message, aucune vente) ; propriétaire : choix parmi les points de vente actifs (présélection : son lieu habituel, sinon le premier) — et « Ventes » (propriétaire) / « Mes ventes » (vendeur), UC-VEN-05 : liste du jour, totaux du serveur (négatifs possibles, signe « − »), filtres période / comptant-crédit / mode / vendeur (propriétaire), recherche n° ou châssis toutes dates, fiche `?id=` (coûts figés et marges pour le propriétaire seulement, « non calculable » si `null`, lus par `saleView.ts`), annulation avec motif (propriétaire), « Signaler une erreur » et réponse (vendeur). **Reçu** (TR-18, D9) : `receipt/` chargé à la demande avec `receipt.css` ; `GET /sales/{id}/receipt` n'est appelé qu'en imprimant (le serveur compte et renvoie « Duplicata » dès la 2ᵉ), puis `window.print()`. Profil lu dans le DTO (`printing.receipt_format` : `58mm` → `thermal-58`, `80mm` → `thermal-80`, `a5`/`a4` → `a4-a5`) ; `@page`, largeur, marge et taille du texte réglées par la boutique posées par un `<style>` ; noir pur, tirets, mentions encadrées en capitales (design-system § 10). « Partager » (PDF) désactivé : « Partage PDF : à venir ». **Prix sous le minimum** (UC-VEN-03, `priceRequests/`) : le vendeur demande l'accord (une demande couvre **un** article : deux articles sous le minimum → « Valider » bloqué avec la raison) ; « En attente » avec le temps restant, état relu **toutes les 10 s** tant que l'écran est ouvert (D19, pas de push) et « Actualiser » ; accordée → la vente part avec `price_request_id` ; refusée → prix à changer ; expirée → nouvelle demande ; chaque raison de `details.price_request` a son message. Propriétaire : carte « Alertes en attente » de l'accueil (nombre relu toutes les 10 s) → `/s/{id}/demandes-de-prix` (article, prix demandé, minimum, écart, vendeur, temps restant ; Accepter / Refuser puis « Oui, … »). **Retours et échanges** (UC-VEN-09, `returns/`, propriétaire, `?id=…&vue=retour`) : quantités bornées par « encore rendable », Vendable / Abîmé, châssis à choisir sur une ligne rendue en partie, motif obligatoire ; retour simple : remboursement plafonné et baisse de créance calculés à titre indicatif (`returnMath.ts`, mêmes règles que le serveur) ; échange : nouvelle vente composée avec les cartes de « Nouvelle vente » (au comptant, même client, même vendeur, lieu d'origine), différence à payer ou à rendre ; la fiche liste les retours (marge retirée pour le propriétaire seulement) et masque « Annuler la vente » dès qu'un retour existe (avec la raison). Écrans chargés à la demande ;
- `src/features/catalog/` : catalogue (UC-STK-01 à 04), onglet « Articles » de la section « Stock » du propriétaire et du comptable (`/s/{shopId}/stock?vue=articles`, fiche `?article={id}`, création `?article=nouveau`), branché sur l'API réelle via `core/gateways/httpCatalogAdmin.ts` ;
- `src/features/stock/` : section « Stock » (chargée à la demande, API réelle via `core/gateways/httpStock.ts`) — matrice (UC-STK-05, écran d'arrivée du propriétaire, du comptable et du vendeur), et pour le propriétaire et le comptable seulement : historique d'un article (`?vue=mouvements&id=`), ajustement (`?vue=ajustement`), inventaire (`?vue=inventaire[&id=]`), valeur du stock (`?vue=valeur`), stock abîmé (`?vue=abime`). Ce que voit chaque rôle passe par `stockView.ts` (le type de la vue vendeur n'a aucun champ de coût). **360 px** : la matrice est rendue en **cartes par article** (un lieu par ligne, puis « En route » et « Total ») et non en table : une table article × lieux ne tient pas à 360 px, et une table défilante cacherait les colonnes ; aucune largeur fixe, libellés et valeurs passent à la ligne. Inventaire : la quantité théorique n'est jamais lue pendant le comptage ; elle apparaît après validation (le serveur désigne d'abord les écarts sans motif, sans révéler le théorique, puis l'écran des écarts s'affiche) ;
- `src/features/purchasing/` : section « Achats » (chargée à la demande, API réelle via `core/gateways/httpPurchasing.ts`), entrée « Achats » du comptable et « Plus → Achats » du propriétaire ; vendeur et chauffeur : « Page introuvable », aucun appel. Vues dans l'adresse (`purchasingNav.ts`) : liste (`/s/{id}/achats`, mois en cours, totaux du serveur, « Afficher plus »), `?vue=nouvel` (saisie **sur un seul écran** : fournisseur avec création rapide, date, lieu, lignes, « Plus de détails » pour frais / facture / note, récapitulatif), `?vue=fiche|corriger|paiement&id=`, `?vue=fournisseurs|fournisseur|fournisseur-nouveau|fournisseur-modifier`. « Créer l'article » réutilise `catalog/ArticleCreateForm` dans le flux. **Coût unitaire final** : calculé côté écran à titre **indicatif** pendant la saisie (`costing.ts`, même règle que `backend/app/domain/purchasing/costing.py` : total de ligne et coût au franc le plus proche demi vers le haut, frais au prorata avec le reste à la ligne de plus forte valeur, yards → mètres au dixième), puis la fiche n'affiche que les chiffres de la réponse. Écart de prix (`PRICE_GAP_CONFIRMATION_REQUIRED`) : confirmation explicite puis renvoi avec `confirm_price_gap: true` et le même `id`. Lieu par défaut : réglages lus par le propriétaire ; le comptable (qui ne lit pas les réglages) envoie « lieu habituel » et le serveur l'applique. Délai du comptable (J+7) revérifié en jour métier de Douala ;
- `src/features/receivables/` : section « Créances » (chargée à la demande, API réelle via `core/gateways/httpReceivables.ts`), entrée du vendeur et « Plus → Créances » du propriétaire ; comptable et chauffeur : « Page introuvable », aucun appel. Vues dans l'adresse (`receivablesNav.ts`) : liste (UC-CRE-04 : total à recevoir, clients débiteurs, versements du jour, tri du serveur par reste décroissant, filtres statut / vendeur (propriétaire) / ancienneté / suivi), `?vue=fiche&id=` (versements annulés barrés avec motif, rappels faits / reportés, garants — pièce d'identité « Pièces jointes : à venir » —, propriétaire : vendeur responsable, annulation de versement, mise en perte), `?vue=versement[&id=]` (bouton « Versement » de l'accueil vendeur : recherche du client puis sa créance, la plus ancienne par défaut ; reste après versement affiché avant validation ; `OVERPAYMENT` → reste du serveur ; reçu `GET /installments/{id}/receipt` imprimé avec les styles du reçu de vente, **profil 80 mm par défaut** car le DTO ne porte pas les réglages d'impression), `?vue=ancienne` (propriétaire), `?vue=releve&client=` (UC-CRE-05) ;
- `src/features/dashboard/` : **accueil de la boutique** (`/s/{shopId}`, chargé à la demande depuis `app/RoleHome.tsx`, API réelle via `core/gateways/httpReporting.ts`, T19). Propriétaire (UC-TDB-01 à 04, design-system § 7.2) : `GET /dashboard?period=…` ; période dans l'adresse (`?periode=yesterday|week|month|last_month|custom&du=&au=`, la période libre est vérifiée comme au serveur : du ≤ au ≤ aujourd'hui à Douala, 366 jours au plus) ; ventes (montant et nombre), argent encaissé, marge en `KpiCard` avec la comparaison en mots (`change_pct` arrondi à l'entier ; `null` → « Pas de comparaison possible (hier : 0 FCFA) ») ; « Voir aussi au CMP » (marge au CMP, écart) ; « N ventes sans coût connu » si > 0 ; dépenses et résultat simple ; créances, stock (valeur au CMP, abîmé, stock bas, à vérifier), éléments du Lot 2 (`{available: false, lot}` → « Disponible au Lot 2 », jamais 0) ; alertes (erreurs signalées → « Ventes », carte existante des demandes de prix). Plusieurs jours : total, moyenne et barres jour par jour (ventes et marge, même échelle, tokens seulement, montants écrits : la barre est décorative). Un appui sur un chiffre ouvre `?detail=sales|payments|expenses|receivables|low_stock` (liste du serveur, total = le chiffre ; fiche de la vente ou de la créance), « Retour à l'accueil ». Autres rôles (UC-TDB-05) : `GET /home`, seul le bloc du rôle est lu (`homeBlock`, fail-fast sinon) — vendeur : « Nouvelle vente », « Versement », ses ventes du jour, ses rappels, saisies en attente ; comptable : Achat, Dépense, Inventaire, « Déplacer du stock » indisponible (« Disponible au Lot 2 »), alertes de stock, valeur du stock, dépenses du jour ; chauffeur : « Disponible au Lot 2 ». **Hors connexion** (RG-T25) : « Chiffres disponibles avec internet » à la place des montants, aussi quand des chiffres étaient déjà affichés (`useFigures` suit l'état du réseau ; rien n'est gardé en mémoire), « Réessayer » ;
- `src/features/auth/` (connexion, connexion admin, changement de code), `src/features/settings/` (Mon compte / Réglages provisoires) ;
- `src/shared/ui/`, `src/shared/format/` ; `src/sw.ts` (service worker) ; `src/testing/` (faux serveur, axe — tests seulement).

Développement de bout en bout : backend sur `127.0.0.1:8000` (voir `../backend/README.md`), `npm run dev` relaie `/api`.
Version affichée : `APP_VERSION` au build, sinon `<version>+<date UTC>`.
